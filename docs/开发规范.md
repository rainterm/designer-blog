## 后端

### 接口路径约定

按"访问方 + 鉴权方式"把 HTTP 接口划分为四段前缀，路由与拦截规则都据此划分：

| 前缀            | 面向                    | 鉴权方式                                                     | 响应体                        |
| --------------- | ----------------------- | ------------------------------------------------------------ | ----------------------------- |
| `/admin-api/**` | 管理后台（admin-web）   | 后台用户登录态（Sa-Token，token 放 `Authorization` 头）      | 统一 `Result`：`{code,msg,data}`   |
| `/app-api/**`   | 前台 / 移动端等公开接口 | 默认**免登录**，由业务自行控制                               | 统一 `Result`：`{code,msg,data}`   |
| `/open-api/**`  | 第三方开放接口（含令牌端点） | OAuth2 `access_token`（`Authorization`，兼容 `Bearer` 前缀）+ 按路径匹配 Scope；其中 `/open-api/oauth2/**` 为令牌端点，免 `access_token`（用 `client_id` / `client_secret` 换取 token） | 统一 `Result`：`{code,msg,data}`；令牌端点返回 RFC 6749 JSON（**不包** `Result`） |

> 后端 8080 只绑定回环、不对外开放，外部流量统一经前端 nginx 的 `/admin-api`、`/app-api`、`/open-api` 前缀转发。
> 令牌端点唯一对外路径为 `POST /open-api/oauth2/token`（同样经 nginx 转发）。

> 单点登录（SSO）的接口、后台配置与目标端最小示例（含可运行案例代码）见 [SSO 接入](SSO.md)。

### 模块与依赖方向（硬约束）

各模块的**直接依赖**：

| 模块 | 直接依赖 |
|---|---|
| `designer-common` | 无（仅第三方库） |
| `designer-framework` | `designer-common` |
| `system-api` / `module-*-api` | `designer-common` |
| `system-service` | `system-api`、`designer-framework` |
| `module-*-service` | `module-*-api`、`designer-framework`；需要 system 能力时依赖 `system-api` |
| `designer-server` | `designer-common`、`system-service`、各 `module-*-service` |

约束：

- `framework` **不得**依赖 `system`；跨层能力由 `framework` 定义扩展接口（如 `PermissionLoader`、`OperLogWriter`），由 **system-service** 提供实现。
- 跨模块只依赖对方 **`*-api`**：`module-*-service` 需要 system 能力时依赖 **`system-api`**，而不是 `system-service`。
- 业务模块：`*-api` 只放 **按需** 的 `*Api` 及 Api 自用入参/出参类型；业务 `model`（entity/dto/vo）与内部 `*Service` 留在 `*-service`。
- `*-service` 在同名 `api` 包实现 `*ApiImpl`（负责 Api 类型 ↔ 内部 model）。
- `designer-server` 是**唯一**的启动组装模块（一个进程），只依赖各 `*-service`。

### 命名约定

- **包结构（系统模块）**：`system-service` 采用**分层优先**——先分层，层内再分业务域：`controller/admin/<域>`、`service/<域>`、`service/<域>/impl`、`mapper/<域>`、`model/{entity,dto,vo}/<域>`；域取 `auth`、`rbac`、`dict`、`config`、`file`、`job`、`log`、`message`、`monitor`。新增类按「层 → 域」归位，不要平铺在层的根目录（`controller/app`、`controller/open` 按接入端划分，保持平铺）。
- **系统域 vs 通用域**：`system` 模块的 controller/service/mapper/entity 统一带 `Sys` 前缀；跨模块通用能力不带 `Sys`（如 `AuthController`、`ProfileController`、`HealthController`）。
- **业务模块**：包名 `com.designer.admin.module.<name>`，权限标识建议 `<name>:<resource>:<action>`。
- **实体**：不加 `Entity` 后缀；DTO 以 `DTO` 结尾；VO 以 `VO` 结尾。

### DTO / VO 优先

- **对外一律强类型**：Controller 入参、Service 返回、跨模块 `*Api` 的入参与出参，只要字段集合在编译期可确定，就必须用 DTO / VO；`Map<String, Object>`、`Result<Map<...>>` 这类「口头约定键名」的写法不允许新增。
- **拼错键名不应静默失败**：Map 的 key 写错只会让前端拿到空值，编译期毫无提示；VO 的字段直接受编译器与 Lombok 保护。
- **协议字段名用注解映射**：确需下划线等非驼峰键名时（如 OAuth2 响应），在 VO 字段上加 `@ONodeAttr(name = ...)`，键名常量仍集中在 `*Consts`，不要为此退回 Map。
- **允许保留 Map 的例外**（仅限「运行时才知道有哪些键」）：
  - Provider / 通道的动态配置项（`StorageConfigSaveDTO#config`、`StorageRuntimeConfig#props`、`FileStorageProvider#validateConfig`）；
  - JSON 原文解析（`JsonUtil#toMap`）；
  - 以 ID、日期等做 key 的内部查找表 / 分组表，它们不是报文。
  即使是这些例外，也要在字段或方法 Javadoc 中写明「为什么必须是 Map」。

### 方法命名（对齐《阿里巴巴 Java 开发手册》）

- **动词前缀按语义固定**：取单个对象 `get`、取多个对象 `list`、统计 `count`、新增 `add` / `insert`、删除 `remove` / `delete`、修改 `update`。
  - `getDetail` / `getById` / `getBySlug`；`listPage` / `listOptions` / `listTree` / `listEnabled`；`countPending` / `countUnread`。
  - `add` / `addType` / `addJobLog`；`remove` / `removeAll` / `removeOlderThan`；`update` / `updateStatus` / `updateDefault`。
  - 不要用 `save` 命名「只新增」的方法：`save` 语义上表示「新增或修改」，只在 `upsert` 语义下使用。
- **分页方法统一 `listXxxPage(...)`**：分页返回的仍是多个对象，用 `list` 前缀；不要写成 `page` / `typePage` / `dataPage` 这类以名词开头的名字。
- **布尔判定用 `is` 前缀**：`isUsernameAvailable`、`isCommentEnabled`、`isCaptchaRequired`。
- **不要用 `get` 拼列表**：`getRouters`、`getReservedNicknames` 这类返回集合的方法改成 `listRouters` / `listReservedNicknames`。
- **业务动作保留业务动词**：`login` / `logout` / `publish` / `audit` / `reply` / `assignMenus` / `resetPassword` / `upload` / `download` 不强行套 `save` / `update`。
- **framework SPI 方法名是实现契约**：`JobLogWriter#write`、`OperLogWriter#writeAsync`、`MessageRecordWriter#recordAsync` 由 framework 定义，实现类必须沿用原名（属于规则例外）。
- **注释只写在接口上**：实现类重写接口方法时不再重复 Javadoc（`@Override` 本身已说明来源）；实现特有的补充说明用行内 `//` 写在方法体内，不写成方法级 Javadoc。

### 数据访问规范

- **Mapper 父接口**：所有 mapper 继承 `MPJBaseMapper<T>`。
- **单表查询**：优先 `LambdaQueryWrapper`；mapper 不出现 `@Select` 等注解。
- **关联查询**：用 mpj 链式 API，优先写在 mapper 的 `default` 方法里。

### 缓存规范

- **Redis 键字面量只允许出现在常量类**：framework 级见 `framework.redis.RedisKeyConsts`，系统模块见 `system.constant.SystemRedisKeyConsts`，博客模块见 `module.blog.constant.BlogRedisKeyConsts`；业务类一律引用常量拼接。
- **键名是数据契约**：上线后只允许新增键，不允许改已有键的前缀 / 结构。改名等于让旧键变成永远不会再被读取的垃圾。
- **拼键统一用 `RedisKeyConsts.SEPARATOR`**：不要在业务类里再写 `":"`，否则分隔符调整时无法一次改完。

### 常量规范

- **常量放在 `constant` 包，不放在接口和实现类里**：接口只保留方法声明，实现类只保留方法实现。
  - framework 级：`framework.constant.*`（如 `HttpConsts`、`MessageChannelConsts`）、`framework.redis.RedisKeyConsts`、`framework.job.ScheduleConsts`。
  - 系统模块：`system.constant.*`（`SysConfigConsts`、`SysSettingConsts`、`SysMenuConsts`、`SysNoticeConsts`、`SysMessageConsts`、`SysFileConsts`、`OnlineUserConsts`、`LoginAttemptConsts`、`Oauth2Consts`、`SsoConsts` 等）。
  - 博客模块：`module.blog.constant.*`（`BlogCommentConsts`、`BlogPostConsts`、`BlogVisitConsts`、`BlogSettingConsts`、`BlogViewConsts`、`BlogRedisKeyConsts` 等）。
- **跨类 / 跨层的值必须抽常量**：默认值、长度上限、状态码、类型标识、请求头名、协议前缀、Redis 键、配置键。判断标准不是「是不是字面量」，而是「同一个值是否在第二处出现，或是否与数据库列宽 / 前端约定对齐」。
- **状态值优先复用 `SystemConsts`**：通用启用 / 停用状态用 `SystemConsts.STATUS_ENABLE` / `STATUS_DISABLE`，不要再写 `1` / `0`；业务专属状态（评论待审 / 通过 / 拒绝等）放在对应模块常量类。
- **只在一个方法内使用、且没有外部语义的值可以留在原地**：正则 `Pattern`、`Comparator`、`DateTimeFormatter`、单例对象（`SecureRandom` 等）属于实现细节，不需要放进常量类。
- **常量类写法**：`public final class XxxConsts` + 私有构造方法，成员 `public static final`，逐项写 Javadoc；键名类常量上线后只增不改。

## 前端

技术栈：Vue 3（组合式 API）+ Naive UI + Vite + Pinia，工程位于 `designer-ui/admin-web`，路径别名 `@` → `src`。

### 目录与模块组织

```
src/
├── api/           # 壳层接口：request / auth / monitor
├── components/    # 全局通用组件（部分在 main.js 全局注册）
├── composables/   # 可复用组合式函数 useXxx
├── constants/     # 常量
├── directives/    # 全局指令（permission）
├── layout/        # 布局壳（侧栏 / 顶栏 / 页签 / 消息中心）
├── modules/       # 业务模块，按模块隔离
│   └── <module>/
│       ├── api/       # 该模块接口
│       └── views/     # 该模块页面
├── router/        # 路由与动态路由注册
├── store/         # Pinia store
├── styles/        # 全局样式
├── theme/         # 主题与品牌
├── utils/         # 工具函数
└── views/         # 壳层页面（login / dashboard / profile / error）
```

- 业务代码一律放进 `modules/<module>/`，不要污染壳层目录；模块内可自行增加 `components/`、`utils/`（参考 `modules/demo`）。

### 命名规范

- **`.vue` 组件**：PascalCase 文件名，如 `PageTable.vue`、`AttachmentUploader.vue`。
- **`.js` 文件**：camelCase，如 `pageLoading.js`、`noticeLink.js`。
- **组合式函数**：`composables/useXxx.js`，导出 `useXxx()`。
- **常量**：`UPPER_SNAKE_CASE`。
- **样式类名 / CSS 变量**：kebab-case。

### 请求与接口

- 统一走 `@/api/request`（axios 实例）：
  - `baseURL` 取 `VITE_API_BASE`（默认空，走同源 / 代理）；
  - 请求头 `Authorization` 直接放 token 原值（本项目约定，未带 `Bearer` 前缀）；
  - `FormData` 自动去掉 `Content-Type`，交由浏览器带 multipart boundary。
- 后端统一响应体 `{ code, msg, data }`：`code === 200` 视为成功；`401` 清 token 并跳登录页；其余弹 `message.error` 并 reject。非统一结构（如文件流）原样返回。
- 接口按模块放在 `modules/<module>/api/`，函数命名 `pageXxx / getXxx / createXxx / updateXxx / deleteXxx`：

  ```js
  import request from '@/api/request'

  export const pageUsers = (params) => request.get('/admin-api/system/user/page', { params })
  export const createUser = (data) => request.post('/admin-api/system/user/add', data)
  ```

- 管理端接口前缀 `/admin-api`，公开前台接口前缀 `/app-api`，开放接口前缀 `/open-api`（详见 [接口路径约定](#接口路径约定)）。

### 路由与权限

- 常量路由写在 `router/index.js` 的 `constantRoutes`；登录后按后端下发的菜单树动态注册。
- 后端菜单 `component` 字符串解析约定：`{module}/{path}` → `src/modules/{module}/views/{path}.vue`
  （例如 `system/user/index`、`demo/index`）；`Layout` 表示目录分组。
- 隐藏页（编辑 / 详情 / 对话等）对应菜单 `visible=0`：注册路由但不进侧栏。
- 按钮级权限用指令 `v-perm`，无权限时元素直接移除：

  ```html
  <n-button v-perm="'system:user:add'">新增</n-button>
  ```

### 状态管理

- 使用 Pinia，文件 `store/<name>.js`，`defineStore('<name>', ...)`。
- 需要持久化的状态自行读写 `localStorage`（参考 `store/app.js` 的 `persist()`）。
- `store/user.js` 持有 token、用户信息、角色 / 权限、动态路由；权限判断用 `userStore.hasPerm('xxx')`。

### 组件与复用

- 通用组件放 `src/components/`，跨模块通用的可在 `main.js` 全局注册（如 `PageTable`、`Dialog`、`DetailDrawer`）。
- 可复用逻辑抽到 `composables/useXxx.js`，不要复制粘贴。
- 列表页优先复用 `PageTable` + `SearchBar` + `PaginationBar` 组合。

## 二次开发（新增业务模块）

以后端新增业务 `foo` 为例，**不要修改** `common` / `framework` / `system`：

1. **后端**：复制 `designer-module-demo` → `designer-module-foo`（含 `foo-api` / `foo-service`），改 `artifactId` 与包名；跨模块能力用 `...api.XxxApi` 按需暴露
2. 根 `pom.xml` 的 `<modules>` 与 `dependencyManagement` 增加父模块及 `foo-api` / `foo-service`；`designer-server/pom.xml` 增加对 `foo-service` 的 `<dependency>`
3. **前端**：复制 `designer-ui/admin-web/src/modules/demo` → `src/modules/foo`
4. **菜单 / 表结构**：在 `sql/init/mysql/<module>/` 增加 SQL，并把模块名加入 `00-run-init.sh` 的 `MODULES`
5. 重新 `mvn -pl designer-server -am package` 与前端构建

详细说明见 [designer-module-demo/README.md](../designer-module-demo/README.md)。
