## 一、总体结论

**综合评分：7.2 / 10**

这是一个**架构设计良好的模块化单体脚手架**，工程素养明显高于同类后台管理系统：

- 分层边界不是靠目录约定，而是靠 Maven 依赖方向 + SPI 反转**强制**保证；
- 扩展点（存储、消息通道）用自描述元数据 + 注册表实现真正的开闭原则；
- 安全细节（路径穿越、Content-Type 推导、下载 Cookie 隔离、可信代理解析）考虑得比多数开源项目深；
- 注释解释的是「为什么这么做」，而非「这行代码做了什么」。

但它目前更接近一个**优秀的开发起点**，尚不是能直接承载核心生产流量的平台：

- 零自动化测试、零 CI/CD；
- 无数据库版本迁移机制；
- 缺少指标、追踪与真实就绪探针；
- 存在三处单机假设，阻断水平扩展；
- 有两处可直接利用的权限问题（登录锁定绕过、垂直越权）。

**结论**：适合作为团队内部项目的起点；在补齐 P0 项之前，不建议直接承载核心生产流量。

## 三、架构骨架

本质是一个**边界清晰的模块化单体**：单进程、单 MySQL、单 Redis，用 Maven 依赖方向与 SPI 维持模块边界。对中小团队而言，这是比微服务更合理的起点。

```
浏览器 / 第三方客户端
        │
        ▼
   ┌─────────────────────────────────────────┐
   │ Nginx：静态资源 / 反向代理 / 限流 / SSE │
   └─────────────────────────────────────────┘
        │  /admin-api  /app-api  /open-api
        ▼
   ┌──────────────────────────────────────────────────────┐
   │ Solon 单进程                                          │
   │                                                       │
   │  Filter 链                                            │
   │    GlobalExceptionFilter → SaToken → OpenApiScope     │
   │                                                       │
   │  30 个 Controller                                      │
   │        │                                              │
   │        ▼                                              │
   │  28 个 ServiceImpl（system-service / module-*-service）│
   │        │                                              │
   │        ▼                                              │
   │  framework SPI（由 system-service 实现）              │
   │    PermissionLoader / OperLogWriter /                 │
   │    FileStorageProvider / MessageChannelProvider       │
   └──────────────────────────────────────────────────────┘
        │                    │                    │
        ▼                    ▼                    ▼
     MySQL 8              Redis 7          本地磁盘 / S3
                            │
                            ▼
                     Quartz（RAMJobStore）
```

### 模块依赖方向（硬约束）

| 模块 | 直接依赖 |
|---|---|
| `designer-common` | 无（仅第三方库） |
| `designer-framework` | `designer-common` |
| `system-api` / `module-*-api` | `designer-common` |
| `system-service` | `system-api`、`designer-framework` |
| `module-*-service` | `module-*-api`、`designer-framework`；需要 system 能力时依赖 `system-api` |
| `designer-server` | `designer-common`、`system-service`、各 `module-*-service` |

关键约束：`framework` **不得**依赖 `system`。跨层能力由 `framework` 定义接口，由 `system-service` 提供实现。

## 四、值得肯定的设计

### 4.1 依赖倒置的扩展点

`designer-framework` 定义 `PermissionLoader`、`OperLogWriter`、`FileStorageProvider`、`MessageChannelProvider` 等接口，`system-service` 提供实现。

这是整套代码**最有价值的架构资产**：框架层不反向依赖业务层，使得「框架能力」与「业务实现」可以独立演进，也天然支持多模块二次开发。

### 4.2 可插拔 Provider

存储与消息通道用 `type()` + `configFields()` 自描述：

- `type()` 声明通道类型；
- `configFields()` 声明配置字段（含类型、默认值、帮助文本），前端据此**动态渲染配置表单**；
- 注册表在启动时自动发现所有实现，按 `type` 装配。

新增 OSS、短信、飞书时，**不需要修改核心流程**——这是典型的开闭原则落地。

### 4.3 安全纵深细节

| 机制 | 实现要点 |
|---|---|
| 密码存储 | BCrypt（`at.favre.lib`，COST=10），与历史哈希兼容 |
| 路径穿越 | 双重校验：Provider 层 `startsWith(root)` + Service 层路径白名单正则 |
| 上传类型 | 不采信客户端声明的 Content-Type，由扩展名白名单推导 |
| 下载安全 | `X-Content-Type-Options: nosniff` + `Content-Security-Policy: default-src 'none'; sandbox` |
| 下载鉴权 | 独立 `HttpOnly` Cookie，`Path` 限定到下载前缀，不放开全局 Cookie 鉴权 |
| 真实 IP | `TrustedProxyHostUtil` 只信任可信代理网段，不可信对端直接忽略转发头 |
| 限流 | Redis Lua 固定窗口，原子操作且能自愈「无 TTL」脏键 |
| 配置密钥 | Solon Vault AES 加密，未配置主密钥时保持明文兼容历史数据 |

### 4.4 代码可读性

- 注释解释「为什么」，例如：为什么 `expire` 不能写在写命令之后、为什么下载 Cookie 不能全局开启、为什么限流要 fail-open；
- 魔法值收敛到常量类（`SystemConsts`、`SysFileConsts` 等）；
- 统一响应体、全局异常、分页封装、逻辑删除、字段自动填充。

### 4.5 部署细节

- 后端只绑定 `127.0.0.1`，所有流量必须经 Nginx，避免绕过代理伪造 IP；
- Nginx **覆写**而非追加 `X-Forwarded-For`，丢弃客户端伪造链；
- 限流返回 `429`，与应用层 `@RateLimit` 语义一致；
- 容器非 root 运行，健康检查与日志滚动齐备。

### 4.6 前端模块化

- `modules/<module>` 目录隔离，业务代码不污染壳层；
- `import.meta.glob` + 后端菜单驱动动态路由；
- 通用组件（`PageTable` / `SearchBar` / `Dialog`）与 composables 复用充分；
- 全仓未使用 `v-html`，降低 XSS 面。

## 五、问题清单

- **P0**：上线前必须处理
- **P1**：进入生产或扩容前处理
- **P2**：可持续演进的架构债

### 5.1 P0 —— 上线阻断项

#### P0-1 登录锁定未绑定来源 IP，且可被大小写变体绕过（已修复）

**原始问题**：`LoginAttemptServiceImpl` 直接用原始用户名拼 Redis 键，锁定只有「用户名」一个维度：

```java
// 改造前：designer-module-system/.../service/auth/impl/LoginAttemptServiceImpl.java
String user = username.trim();
...
String failKey = SystemRedisKeyConsts.LOGIN_FAIL_PREFIX + user;
long count = redisCounter.incrWithTtl(failKey, failTtl);
```

而数据库排序规则为 `utf8mb4_general_ci`（`sql/init/mysql/_base/database.sql`），账号查询**大小写不敏感**。

**形成机制**：

```sql
-- 数据库：Admin 命中 id=1 的 admin
SELECT id FROM sys_user WHERE username = 'Admin';

-- Redis：键是大小写敏感的
login:fail:admin  -> 5   （已锁定）
login:fail:Admin  -> 0   （全新窗口）
```

这里其实是两个独立缺陷：

1. **锁定维度缺少 IP**：任何人只要知道账号名，输错 5 次就能把别人的账号锁住 —— 一个零成本的定向 DoS；
2. **大小写变体**：`Admin` / `ADMIN` 照样命中 `admin`，但 Redis 键不同，锁定与验证码阈值同时失效。

**修复（已落地）**：

1. **锁定改为「账号 + 来源 IP」组合**：`login:pair:lock:{ip}:{username}`，TTL 为锁定时长。
   攻击者只能锁住自己这个来源，账号主人从自己的网络登录不受影响。IP 统一取
   `ClientIpUtil.normalize(ctx)`，与 `@RateLimit` 使用同一份可信解析结果（多级代理取首段）。
2. **新增 IP 维度计数与锁定**：`login:ip:fail:{ip}` / `login:ip:lock:{ip}`，
   默认 30 次 / 10 分钟，拦住「一个密码试多个账号」的密码喷洒。
   阈值高于单账号，避免 NAT / 办公网共用出口被个别用户连坐。
3. **账号维度计数不再触发锁定**：`login:acct:fail:{username}` 跨 IP 累计，
   只用于决定「要不要出滑块」。否则分布式撞库依然可以把目标账号锁死。
4. **账号区分大小写**：查询仍按库表（`ci`）取出候选行，随后在 Java 侧做一次原文比较，
   大小写不完全一致即视为账号不存在。注册侧唯一性校验保持不区分大小写，
   避免出现 `admin` / `Admin` 这类仿冒账号。
5. **无法解析来源 IP 时跳过 IP 维度**：不把 `unknown` 当作计数键，
   避免所有无 IP 请求共用一个计数器、被刷到阈值后集体误伤。

**遗留权衡**：分布式撞库仍可通过账号维度把验证码「刷出来」（受害者需要多滑一次），
但账号不会被锁死；彻底缓解需要接入设备指纹 / 风控评分，属 P2 范畴。

#### P0-2 权限边界缺失，存在垂直越权

**证据**：`UserSaveDTO` 同时包含 `password`、`status`、`roleIds`，而 `update` 只要求 `system:user:edit`：

```java
// designer-module-system/.../service/rbac/impl/SysUserServiceImpl.java:154
public void update(UserSaveDTO dto) {
    ...
    if (notBlank(dto.getPassword())) {
        user.setPassword(PasswordUtil.encode(dto.getPassword()));
    }
    userMapper.updateById(user);
    if (dto.getRoleIds() != null) {
        saveUserRoles(dto.getId(), dto.getRoleIds());
    }
}
```

**影响**：拥有「编辑用户」权限的账号可以：

1. 绕过 `system:user:resetPwd` 直接修改他人密码；
2. 停用超级管理员；
3. 将超级管理员角色授予任意账号（`saveUserRoles` 不校验角色可授予性）。

**建议**：

- 密码只能走独立的 `resetPwd` 通道，`update` 忽略 `password` 字段；
- 状态修改单独走 `updateStatus` 并校验超管保护；
- 角色授予增加「不能授予高于自己的角色」校验；
- 超管保护基于 `is_super` 而非硬编码 `id == 1`。

#### P0-3 零自动化测试、无 CI/CD

**证据**：

- 仓库无 `src/test` 目录；
- POM 无 JUnit / Testcontainers / Mockito；
- 前端 `package.json` 无 Vitest / Playwright；
- 无 `.github/workflows`、Jenkinsfile 或等价流水线配置。

**影响**：任何重构、依赖升级、SQL 变更都只能靠手工回归；质量与交付节奏不可控。

**建议**：

1. 后端先补三类测试：鉴权/权限的集成测试、登录链路的单元测试、Service 层的 DB 集成测试（Testcontainers）；
2. 前端补 Vitest（工具函数、composables）+ Playwright（关键链路：登录、用户 CRUD、权限控制）；
3. 接入 CI：`mvn verify` + `pnpm build` + `pnpm lint`，PR 必须通过。

---

#### P0-4 没有数据库版本迁移机制

**证据**：

- `sql/upgrade` 为空目录；
- 初始化脚本是 `DROP TABLE` 重建，只适用于首次初始化；
- 文档明确标注为「破坏性初始化」。

**影响**：生产升级不可重复、不可回滚；多环境表结构容易漂移；发布流程中最不可控的一环。

**建议**：引入 Flyway 或 Liquibase，把现有 `schema.sql` 转为基线（baseline），后续变更新增版本化脚本，纳入 CI 校验。

### 5.2 P1 —— 生产化与扩容

| 编号 | 问题 | 证据 | 影响 |
|---|---|---|---|
| P1-1 | 站内信全表加载 + 内存分页 | `SysNoticeServiceImpl.visiblePublished` 每次 `selectList` 全部可见消息，再 Java 内 `filter` / `subList`；`receivers` 为逗号字符串 | 消息量与用户数增长后，inbox 与未读数轮询成本线性上升，无法命中索引 |
| P1-2 | 权限每次鉴权都查库 | `StpInterfaceImpl` → `SysPermissionLoader`：非超管每次 `@SaCheckPermission` 至少 2 次 SQL（`isSuper` + `perms`） | 高频接口鉴权开销随 QPS 放大，数据库成为隐性瓶颈 |
| P1-3 | 水平扩展存在三个单机假设 | `NoticeSseHub.sessions` 为进程内 `ConcurrentHashMap`；Quartz 为 `RAMJobStore` + `NON_CLUSTERED`；启动时每实例各自加载全部任务 | 多实例部署时 SSE 消息只到部分节点；定时任务重复执行 |
| P1-4 | Token 可通过 query 参数传递 | `app.yml:153` `sa-token.is-read-param: true` 为全局开关（本意是给 EventSource 的 SSE 用） | Token 可能进入 URL、访问日志、Referer 与浏览器历史，泄露面扩大 |
| P1-5 | 可观测性不足 | 仅有文件日志；`/health` 返回固定 `UP`，不探测 MySQL / Redis；无 Micrometer、Tracing、告警规则 | 无法量化错误率、P95 延迟、连接池与队列水位；依赖故障时健康检查仍报健康 |
| P1-6 | 前端会话与浏览器安全缺少纵深 | Token 存 `localStorage`；Nginx 未配置 CSP、`X-Frame-Options`、`Referrer-Policy` | 一旦出现 XSS（依赖、富文本、第三方脚本），会话可被直接读取，目前没有第二道防线 |

**P1-1 补充**：`receivers` 用逗号字符串存储接收人，导致「按人查询」只能全表扫描后内存过滤。建议改为 `sys_notice_receiver` 关联表，配合 `(user_id, notice_id)` 索引与数据库分页。

**P1-3 补充**：这是当前**最主要的扩容阻断项**。改造方向：

- SSE → Redis Pub/Sub（或按用户一致性哈希路由）；
- Quartz → JDBC JobStore + 集群模式，或改为分布式调度（如 XXL-Job）；
- 启动加载任务需加分布式锁或改为按需注册。

**P1-4 补充**：建议关闭全局 `is-read-param`，仅在 SSE 端点通过 `SaRouter.match` 局部放开 query token，并缩短该类 token 的有效期。

### 5.3 P2 —— 架构债

| 编号 | 问题 | 证据 | 影响 |
|---|---|---|---|
| P2-1 | RBAC 只到功能权限，没有数据权限与租户隔离 | 全仓无 `data_scope` / `tenant` 字段或拦截逻辑；列表查询未按部门或本人过滤 | 企业常见的「本部门 / 仅本人」数据隔离需二次开发，越权风险由业务模块各自兜底 |
| P2-2 | 定时任务反射面过大 | `JobInvokeUtils` 只校验 bean 是否存在，方法名与参数由后台字符串解析后反射调用 | 拥有任务管理权限的账号可调用容器内任意 Bean 方法；应限制到白名单接口或包 |
| P2-3 | 批量写与 N+1 查询 | 用户角色、角色菜单、消息已读均逐条 `insert`；菜单删除按层 BFS 查询；按角色筛选用户先查全量关联再 `IN` | 数据量上升后写放大与往返次数明显，长事务持有连接时间变长 |
| P2-4 | 硬编码超级管理员 ID = 1 | `SysUserServiceImpl.remove` / `updateStatus` 用 `id == 1` 判断超管；`update` DTO 又可绕过该判断改状态 | 与 `is_super` 模型不一致；换库、导入数据或新增超管后保护失效 |

## 六、架构层面的判断

### 1. 模块化单体是正确取舍，不要急着拆微服务

当前边界靠 Maven 依赖与 SPI 维持，成本低、可验证。真正阻断扩容的是 SSE / Quartz / 权限查询三个单机假设，而不是「没有微服务」。

在单体内部把模块边界做扎实，比过早引入分布式复杂度更符合团队规模。

### 2. 安全能力「点」很强，「面」不足

单个机制（BCrypt、路径校验、Cookie 隔离、可信代理）做得很好，但权限边界、会话暴露面与数据级隔离没有形成体系。

安全需要按「**谁能对谁做什么**」统一建模，而不是逐点加固。本次发现的两个 P0 都属于「机制正确、策略缺失」。

### 3. 数据访问层缺少规模化约束

单表 CRUD 规范统一，但站内信的内存分页、权限的每请求查库、关联表的逐条写入，都是「**功能正确、容量不正确**」的典型问题。

这类问题在小数据量下不会暴露，一旦上线就会集中出现。

### 4. 交付链路是最大短板

代码质量再高，没有测试与 CI 也无法在持续迭代中保持；没有迁移工具，数据库会成为发布流程中最不可控的一环。

测试、CI、迁移工具三者缺一，会持续侵蚀前面所有优点。

## 七、改进路线图

### 第 1 阶段 · 止血（1–2 周）

- [ ] 登录计数键改用 `userId` 或统一小写归一
- [ ] 收回 `update` 接口对 `password` / `status` / `roleIds` 的写入能力
- [ ] 超管判断统一走 `is_super`，移除硬编码 `id == 1`
- [ ] 角色授予增加可授予性校验
- [ ] 为上述三条补回归测试，并接入 CI

**验收标准**：`Admin` 与 `admin` 共享同一锁定计数；仅持 `system:user:edit` 的账号无法改密码、停用超管、授予超管角色。

### 第 2 阶段 · 生产化（1–2 月）

- [ ] 引入 Flyway / Liquibase，建立基线并纳入 CI
- [ ] 站内信改为接收人关联表 + 数据库分页
- [ ] 权限缓存与失效策略（变更角色时主动清理）
- [ ] 接入 Micrometer + 就绪探针（探测 MySQL / Redis）
- [ ] SSE 改 Redis Pub/Sub
- [ ] 定时任务加集群锁或改分布式调度
- [ ] 局部放开 SSE 的 query token，关闭全局 `is-read-param`

**验收标准**：多实例部署下 SSE 消息全量可达、定时任务不重复执行；数据库升级可重复执行且可回滚。

### 第 3 阶段 · 平台化（3–6 月）

- [ ] 抽象数据权限与租户模型
- [ ] Token 升级为短时 + 刷新，或改 BFF / HttpOnly
- [ ] 补 CSP 与安全响应头
- [ ] 建立 API 契约、ADR 与容量基线
- [ ] 定时任务调用目标白名单

## 八、附录

### 8.1 统计口径

- Java 行数：`designer-common` / `designer-framework` / `designer-module-system` / `designer-module-demo` / `designer-server` 的源码合计，不含 `target/`；
- 前端行数：`designer-ui/admin-web/src` 下 `.vue` 与 `.js` 合计，不含 `dist/`；
- 数据表与索引来自 `sql/init/mysql/system/schema.sql`。

### 8.2 评分说明

评分是**架构判断**，不是代码覆盖率或性能压测结果。权重反映「脚手架被二次开发时的长期成本」：

- 模块化与安全各占 20%，因为它们决定二次开发是否会被迫腐化；
- 测试与交付虽占 10%，但它决定前两项能否持续成立。

### 8.3 未覆盖范围

- 真实并发与容量压测；
- TLS / 网关层配置；
- 第三方依赖漏洞扫描；
- 运行实例上的越权与绕过验证（P0-2 基于源码静态分析推断，建议实测确认后修复；P0-1 已完成改造，仍需在真实代理链路上验证取到的客户端 IP）。
